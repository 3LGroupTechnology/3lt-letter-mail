# DEPLOY.md — 3LT Letter Mail · Deploy-Night Runbook

The mechanical checklist for deploying `main` of this repo to the
production server (the box serving **https://3lgrouptechnology.com**).
The stack is one Docker Compose service: the entrypoint runs the REST API
(`uvicorn api:app`, :8000) and the MCP server (`mcp_server.py`, :8001)
side by side in one container, behind a TLS reverse proxy.

Read the three ⚠️ blocks before touching anything. Work top to bottom;
every step is checkable.

---

## ⚠️ 1. The shared library is NOT in this repo — ship it or nothing boots

`api.py`, `core.py`, and `mcp_server.py` import `tlt_billing`,
`tlt_approvals`, `tlt_tiers`, `tlt_receipts`, `tlt_risk`, and `tlt_mailer`
from the **sibling `3lt-shared/` directory**, which lives OUTSIDE this
repository and is not versioned with it. In production the Dockerfile does
`COPY . ./`, so **`3lt-shared/` must be copied into this repo's directory
before the image is built**, landing at `/app/3lt-shared` inside the
container (`.env` sets `TLT_SHARED_DIR=/app/3lt-shared`). The directory is
gitignored here on purpose — copy it, build, never commit the copy.

Deploy-night consequence: **the `tlt_billing.py` you ship is the billing
code that runs.** The fax-billing work (`settle_fax`) lives in that shared
file, not in this repo. Copy the CURRENT shared tree, not a stale one, and
verify after copying:

```bash
grep -n "def settle_fax" 3lt-shared/tlt_billing.py   # must print a line
```

## ⚠️ 2. Billing is Stripe TEST-MODE ONLY in this build

`tlt_billing` refuses any Stripe secret key that does not start with
`sk_test_` ("this build supports test mode only"). Putting live Stripe
keys in `.env` will NOT enable real charges — billing calls will fail
with that refusal (sends by keys with no payment method still work; they
are audited as unbilled). Lifting the guard is a deliberate code change,
not a deploy setting. **Do not discover this after announcing paid
service.** See Open Questions.

## ⚠️ 3. Known drift: the live `/docs.html` has no repo counterpart

The currently deployed site serves a `/docs.html` page that **does not
exist anywhere in this repo** (no route, no file). The deployed tree is
ahead of / different from the repo. Before overwriting anything on the
server, capture what is actually running (see Step 0) and reconcile:
either the page is generated by something outside this repo (find it and
keep it working), or it gets ported into `dashboard/` as part of a
follow-up change. **Do not let the deploy silently delete it.**

## Step 0 — Pre-flight: see what is actually running

On the production server, before changing anything:

```bash
docker ps                        # is the compose service the live one?
docker compose ps                # from the deployed repo directory
ls                             # what's in the deployed tree that git doesn't know?
cp .env .env.bak-$(date +%F)     # back up the live env FIRST
```

Back up the database volume (keys, drafts, faxes, receipts, audit trail):

```bash
docker run --rm -v lms-data:/data -v "$PWD":/backup alpine \
  tar czf /backup/lms-data-$(date +%F).tar.gz /data
```

Note any server-only files (especially anything producing `/docs.html`)
and keep them aside. If the live box is NOT running this compose stack,
stop and reconcile first — this runbook assumes it is (see Open
Questions).

## Step 1 — Get `main` onto the server

```bash
git fetch origin
git checkout main
git pull origin main
git log --oneline -3             # confirm the expected merge is on top
```

(Fresh install instead: `git clone` this repo, `cp .env.example .env`,
and treat every value in Step 3 as a first-time set.)

## Step 2 — Ship the shared library (see ⚠️ 1)

Copy the current `3lt-shared/` tree into the repo directory so it is
inside the Docker build context:

```bash
# from wherever the canonical 3lt-shared/ lives on the build machine:
cp -r <path-to>/3lt-shared ./3lt-shared
grep -n "def settle_fax" 3lt-shared/tlt_billing.py
ls 3lt-shared/                   # tlt_billing.py, tlt_approvals.py, ...
```

## Step 3 — Env checklist (`.env` on the server)

Every value below must be set deliberately. `.env` is never committed.

| Var | Production value / note |
|---|---|
| `PUBLIC_BASE_URL` | **`https://3lgrouptechnology.com`** exactly — approval links, Connect URLs, OAuth metadata, and the server card are all built from it. The example file's `mail.example.com` placeholder must not survive. |
| `LMS_ADMIN_TOKEN` | Long random secret, stable across deploys. Generate: `python3 -c "import secrets; print(secrets.token_urlsafe(32))"`. Startup refuses to run without it in the container entrypoint. |
| `APPROVAL_TOKEN_SECRET` | Long random secret, stable — if it changes or is unset, all outstanding one-tap Allow/Deny links die. |
| `POSTGRID_API_KEY` | **LIVE** key (`live_...`) for real mail. See the gate below. |
| `ALLOW_LIVE_MAIL` | `1` — a live PostGrid key is REFUSED at startup without it (`mail_provider.guard_live_key`). Test keys need no gate. |
| `POSTGRID_AV_API_KEY` | Optional; blank reuses the Print & Mail key. |
| `MAIL_PROVIDER` | `postgrid` (lob is legacy fallback only). |
| `PHAXIO_API_KEY` / `PHAXIO_API_SECRET` | **LIVE** Phaxio credentials for real faxes. Blank = fax endpoints report not-configured (letters still work). |
| `ALLOW_LIVE_FAX` | `1` — live Phaxio credentials are REFUSED at startup without it (`phaxio_client.guard_live_key`). Flip only after the Step 6 fax smoke test passes on test credentials. |
| `STRIPE_SECRET_KEY` | ⚠️ **Test key only in this build** — see ⚠️ 2. Use the `sk_test_...` key until the guard is lifted by a code change. |
| `STRIPE_PUBLISHABLE_KEY` | Matching publishable key for the `/billing` + `/connect` Payment Element pages. |
| `STRIPE_WEBHOOK_SECRET` | Signing secret for `POST /v1/webhooks/stripe`; the Stripe dashboard webhook endpoint must point at `https://3lgrouptechnology.com/v1/webhooks/stripe`. |
| `LMS_DB_PATH` | `/data/lms.db` (compose volume `lms-data`). Do not change casually — it is where all state lives. |
| `LMS_UPLOADS_DIR` | `/data/uploads` (same volume). |
| `TLT_RECEIPTS_DIR` | `/data/receipts`. |
| `TLT_MAILER_BACKEND` | `log` writes receipt files only. Real receipt email needs a configured backend — see Open Questions. |
| `TLT_SHARED_DIR` | `/app/3lt-shared` (set by `.env.example`; matches Step 2). |
| `LMS_MCP_HOST` / `LMS_MCP_PORT` | `0.0.0.0` / `8001` inside the container (compose default). |
| `POSTGRID_BASE_COST_USD` / `POSTGRID_CERTIFIED_COST_USD` / `PHAXIO_PER_PAGE_USD` | Quote estimates (defaults `0.97` / `9.51` / `0.07`). Providers bill actuals; only change with a pricing-page check in hand. |

## Step 4 — Build + restart

```bash
./deploy.sh
```

`deploy.sh` validates `.env` (provider key + admin token present, no
placeholders), runs `docker compose build`, `docker compose up -d`, and
polls `http://127.0.0.1:8000/health` for up to ~60 s. Equivalent manual
sequence:

```bash
docker compose build
docker compose up -d
docker compose ps
docker compose logs --tail=100
```

Startup failures to expect if the env is wrong: live PostGrid/Phaxio
credentials without their `ALLOW_LIVE_*` gate (refused by design), or a
missing `LMS_ADMIN_TOKEN` (entrypoint refuses). Both are loud in the logs
and both mean "fix `.env`, re-run" — never bypass the guards.

## Step 5 — Post-deploy verification probes

Public surface (from anywhere):

```bash
B=https://3lgrouptechnology.com
curl -s $B/health                       # {"ok": true, ...}
curl -s -o /dev/null -w "%{http_code}\n" $B/            # 200 dashboard
curl -s -o /dev/null -w "%{http_code}\n" $B/billing     # 200
curl -s -o /dev/null -w "%{http_code}\n" $B/privacy.html  # 200
curl -s -o /dev/null -w "%{http_code}\n" $B/connect     # 200 landing
curl -s $B/.well-known/oauth-authorization-server | head -c 300
#   -> JSON, "issuer": "https://3lgrouptechnology.com", empty grant lists,
#      x-3lt-auth scheme "api_key" (truthful: there is no OAuth deployment)
curl -s $B/.well-known/mcp/server-card.json | head -c 300
#   -> JSON server card: name 3lt-letter-mail, remotes[0].url = $B/mcp,
#      7 tools (3 letter + 4 fax). This is what Smithery reads.
```

MCP endpoint (streamable HTTP; protocol-level probe needs no API key —
our auth is the `api_key` argument per tool call):

```bash
curl -s $B/mcp -X POST \
  -H 'Content-Type: application/json' \
  -H 'Accept: application/json, text/event-stream' \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list","params":{}}'
#   -> the 7 tools: draft_letter, request_send, send_status,
#      create_fax_draft, approve_fax, send_fax, get_fax_status
```

Then one real tool call with a test/staff API key (issue one with
`POST /v1/keys` + `X-Admin-Token` if none exists): `draft_letter` for a
letter to a controlled address and `create_fax_draft` for a controlled
number. Confirm quotes come back and nothing sends without approval.

## Step 6 — Smoke tests before flipping live gates

Do these with **test** provider credentials first (or gates at `0`):

1. **Letter loop** — draft → `request_send` → approve (dashboard or
   Allow link) → status `SENT`, provider id present. Test key = simulated
   send, nothing mailed.
2. **Fax loop** — `POST /v1/faxes` (or `create_fax_draft`) → approve →
   send → status `SENT`. Test credentials = simulated, nothing faxed.
3. **Billing loop** — on a key WITH a saved test payment method: one
   letter send and one 1-page fax send; confirm exactly one charge each
   (fax: $1.07 net → $1.42 gross), receipts written/emailed, and spend
   pooling across both rails against the monthly cap.

Then flip the gates one at a time — set the LIVE key, set its
`ALLOW_LIVE_*=1`, `./deploy.sh`, re-run Step 5 probes — and finish with
one real letter to yourself and one real fax to a number you control.
Confirm physical arrival before announcing anything.

## Rollback

```bash
git checkout <previous-good-commit>     # or the pre-deploy tag
cp -r <saved-copy>/3lt-shared ./3lt-shared   # match the code's vintage!
./deploy.sh
```

Database: restore the Step 0 tarball into the `lms-data` volume only if
the deploy corrupted state — a code rollback alone does not need it.
Note the DB migrations are additive (e.g. `billing_receipts.fax_id`), so
older code generally runs against a newer DB; verify with the Step 5
probes either way.

## Ongoing

- **Backups** — repeat the Step 0 tarball on a schedule; `lms.db` holds
  keys, drafts, faxes, receipts, and the audit trail.
- **Logs** — `docker compose logs -f`.
- **Updates** — pull `main`, re-ship `3lt-shared` (Step 2), `./deploy.sh`.
  The `lms-data` volume survives rebuilds.
- **Secrets rule** — `LMS_ADMIN_TOKEN`, provider keys, and Stripe keys
  live in the server `.env` only: never in chat, logs, or git.

## Open questions — what the repo could NOT tell us

Resolve these on/before deploy night; they are gaps in the record, not
in the code.

1. **Production host access.** The repo records no host, user, or key for
   the production server, and no prior deploy transcript. How the box is
   reached (and by whom) must be established before Step 0 can start.
2. **Is the live box actually running this compose stack?** The
   `/docs.html` drift (⚠️ 3) says the deployed tree differs from the
   repo. Step 0 verifies; if it is a different setup (systemd units, a
   hand-run uvicorn, a different directory), this runbook's restart
   steps need translating to match reality before anything is replaced.
3. **Reverse-proxy routing.** No Caddy/Nginx config is in the repo. The
   public surface requires: `/mcp` → :8001, everything else (including
   `/.well-known/*`) → :8000, all over TLS for
   `3lgrouptechnology.com`. Confirm the live proxy does this; the
   server-card and OAuth-metadata probes in Step 5 depend on it.
4. **Stripe live charging.** When does the test-mode guard in
   `tlt_billing` get lifted, and by what change? Until then "paid
   service" runs on test rails (⚠️ 2). Also unrecorded: whether the
   production Stripe account's webhook endpoint + signing secret match
   Step 3's expectation.
5. **Receipt email.** `TLT_MAILER_BACKEND=log` sends no email. Which
   backend/credentials production uses for customer receipt email is not
   recorded anywhere in the repo.
6. **Where the canonical `3lt-shared/` lives** on the build/deploy
   machine, and how it is versioned (it has no git repo of its own in
   this workspace). Step 2 needs a named source of truth, or the shipped
   billing code is whatever happened to be in someone's directory.
7. **Phaxio account state.** The repo assumes live Phaxio credentials
   exist to paste into `.env`. Whether the Phaxio (Sinch) account is
   created, verified, and funded (their $10 minimum) is an account-side
   fact the code cannot see.
